# 実装段階と完了条件

これは実装順の提案で、運営承認済みの日程ではありません。イベント開催日は2026年11月1日なので、全機能を同時に作ろうとせず、紙受付と手入力による最低限の運用を早めに実装・試験する必要があります。

## Phase 0：仕様と運用判断

リポジトリの全体を監査し、仕様の要件、提案、未決定事項を分離します。まずC01〜C08について選択肢と推奨案、業務リスク、必要な運営判断を報告します。紙受付をどう一意識別するか、景品共有、手書き券、障害時の継続条件について承認がないまま、本番動作を断定できるコードを作らないでください。

完了条件：既存コードの差分一覧、判断待ち一覧、最小実装範囲、必要なDB migrationとテスト計画が説明されている。

## Phase 1：開発基盤と純粋なdomain

Node.js/ES Modules、Fastify、設定読み込み、ヘルスチェック、`node:test`、抽選ライン判定を整えます。domain層はHTTPやDBに依存しません。現スターターはライン判定・カード配置データ・ヘルスチェックを含みます。

完了条件：ユニットテスト成功、ヘルスチェック成功、設定不正時に起動を拒否し、実行手順をREADMEに記載している。

## Phase 2：DB、認証、操作記録

SQLite接続、WAL、外部キー、busy timeout、番号付きmigration、トランザクション、監査ログ、セッション、権限、レート制限を実装します。DBスキーマはC04、C21、C22等の決定を反映してから確定します。秘密情報の平文保存やログ出力を禁止します。

完了条件：クリーンDB構築、再起動後の永続化、認証・認可テスト、migrationを使った復元テスト。

## Phase 3：紙カード受付、手入力抽選、共有景品

受付マスの確認・修正、N計算、カード使用済み化、セッション作成を整合するトランザクションで行います。赤・緑・水色・白の玉を順番に記録し、先着N個を有効、超過分を超過とします。要確認玉・景品不足があれば結果確定を拒否します。2台が同時に共有景品を確保しても負数・二重確保を起こさないようにします。

完了条件：仕様書の受入試験01、02、05、06、08、11〜13、15、16、24、25、31〜33および関連する追加試験が実装とテストでカバーされ、運用判断が済んでいる。

## Phase 4：券発行、印刷、引換、手動代替

1セッション1券番号、印刷ジョブの状態、印刷失敗後の再印刷、スタッフによる排紙確認、1回限りの引換、障害時の手書き券を分けて管理します。プリンターの型番・紙幅・ドライバーを確認します。

完了条件：同一券番号で再印刷でき、券と景品確保が二重化せず、手書き券を運用承認に従って照合できる。

## Phase 5：案内・スタッフ画面とリアルタイム更新

台別の状態、色・順番・あと何個、補充・戻し指示、機器状態、監査ログを実装します。SSE再接続時に状態を再取得し、別台の変更やrevision競合を安全に処理します。

完了条件：画面再読み込み・SSE切断・低速回線で状態が復旧し、無音でも情報を理解できる。

## Phase 6：来場者カード、QRスタンプ、アンケート

来場者Cookie、カード発行、QR、スタンプ、アンケートを実装します。⑤の初期達成、同種別複数マスの埋め方、QRの主体、紙参加者のアンケート導線が決定されるまでは、そのルールを仮定した本番動作を作りません。

## Phase 7：立体会場Webマップ

立体的な俯瞰表示は必須です。参考画像だけを表示する、平面図だけで済ませる、外部サイトへリンクする実装では要件を満たしません。ブース図形とラベルを同じIDへ紐付け、選択時に詳細、ステージ選択時に演目タイムラインを開きます。実データがなければ「未登録」「準備中」と表示し、演目やブース情報を創作しません。描画ライブラリは実装前に比較・選定し、スマホ・iPadで試験します。

## Phase 8：C1/C2機器連携と実機試験

手入力経路が合格してから、機器トークン、永続送信キュー、bootId/seq、冪等性、受付世代ID、遅着の要確認経路を加えます。USB帯域、カメラ、Windows会場PC、プリンターを実機で試験します。

## Phase 9：公開、復元訓練、本番リハーサル

Linuxサーバーの専用ユーザー、systemd、Caddy、HTTPS、ファイアウォール、監視、DBと画像のバックアップ、復元を試験します。DNSと大学ネットワークの公開許可は別々に確認します。会場PC停止、サーバー再起動、回線断、手書き券、復旧後の突合せを運営スタッフとリハーサルします。

**リリースゲート：** 受入試験が通ったこと、運営が未決定事項を承認したこと、実機と障害訓練を完了したことは別々に記録します。未実施の実機試験を合格と報告しないでください。

## 依存パッケージの導入方針

最初のスキャフォールドでは、ヘルスチェックに必要なFastifyのみを依存関係に含めています。SQLite、Cookie、静的ファイル配信、QR生成などは仕様上の予定依存ですが、実際の機能を実装する段階で対応バージョンとNode.js互換性を確認して追加してください。未使用のネイティブ依存（特にSQLite関連）を最初から構築して、環境確認前に開発を妨げないようにします。
